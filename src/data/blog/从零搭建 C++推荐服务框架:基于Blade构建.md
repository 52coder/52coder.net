## Table of contents

## 项目背景

这是一套基于 **brpc + DAG 图执行**的 C++ 排序/推荐服务框架，结构上分三层：

| 目录               | 角色                                                                                         |
| ------------------ | -------------------------------------------------------------------------------------------- |
| `rank/`            | 框架层：vvframe DAG 引擎、各种 Manager（Graph/Cache/Transport/DynamicConf）、`Impl` RPC 基类 |
| `rank_services/`   | 业务层：业务 `Node` 子类、业务 proto、`main/main.cpp` 入口                                   |
| `rank/thirdparty/` | 三方依赖：brpc、protobuf、gflags、glog、boost、tinyxml2 等，全部 vendored                    |

构建系统用的是**Blade**。请求处理流程大致是：

```
client request
  → CommonImpl::process()
  → GraphManager::getGraph(name)
  → graph->run(context)        # DAG 节点按依赖顺序异步执行
  → response
```

DAG 拓扑由 `conf/graph.xml` 描述，节点名→类的映射由 `conf/node.xml` 决定，运行期 `DynamicConfLoadMgr` 每 2 秒轮询配置文件做热更新。

## 先匹配预编译依赖的运行平台

本文使用的 `thirdparty/` 快照带有 Linux x86_64 预编译产物，它们不能直接链接进 macOS 程序。这是这份依赖包的约束，不是说 brpc、jemalloc 或 LevelDB 一概不支持 macOS。可以用 `file` 和 `readelf` 检查具体文件。

沿用这些二进制时，需要匹配 Linux x86_64 环境；如果宿主是 Apple 芯片，还应确认容器的平台和仿真设置。可选的环境有：

- Docker / OrbStack 起 Ubuntu 容器
- SSH 到远程 Linux 主机（VS Code Remote-SSH 体验不错）
- 公司内置 CI / 远程 build host

我选第一种，用 OrbStack 起 Ubuntu 22.04。

## 拉代码：注意 Git LFS

`thirdparty/**/*.a` 和 `*.so` 都是用 LFS 存的（见 `.gitattributes`）。如果先 `git clone` 再装 git-lfs，那次 clone 拉到的全是 pointer 文件，链接器会报：

```
/usr/bin/ld: rank/thirdparty/tinyxml2/lib64/libtinyxml2.a: file format not recognized; treating as linker script
/usr/bin/ld: rank/thirdparty/tinyxml2/lib64/libtinyxml2.a:1: syntax error
```

第 1 行是因为 `.a` 实际内容是：

```
version https://git-lfs.github.com/spec/v1
oid sha256:abc...
size 12345
```

链接器收到的是文本指针，无法按静态库格式解析。

**修复**：

```bash
apt install -y git-lfs && git lfs install
cd /workspace
git lfs pull
file rank/thirdparty/tinyxml2/lib64/libtinyxml2.a
# 应输出: current ar archive
```

新机器可以先安装并初始化 Git LFS，再克隆项目。已经克隆的仓库也能通过 `git lfs pull` 补齐对象，不需要因此重拉全部代码。

## 三类编译错误

切到 Ubuntu 22.04 后，`blade build //rank:framework` 出现了多条编译错误。下面按三个原因整理，避免逐条修改连锁报错。

### #1 protobuf 版本不匹配（最关键）

错误现象：

```
options.pb.h: This file was generated by a newer version of protoc
generated_message_bases.h: No such file or directory
PROTOBUF_NAMESPACE_OPEN does not name a type
ConnectionType / ProtocolType / CompressType not declared
tls_stringmap_temp was not declared
```

排查：

```bash
grep "GOOGLE_PROTOBUF_VERSION " thirdparty/protobuf/include/google/protobuf/stubs/common.h
# #define GOOGLE_PROTOBUF_VERSION 3007001       ← 3.7.1
grep "PROTOBUF_VERSION" thirdparty/brpc/include/brpc/options.pb.h
# #if PROTOBUF_VERSION < 3021000                 ← 3.21.x
```

现有 protobuf 头文件标记为 3.7.1，而所用 brpc 生成头要求 3.21.x 级别的接口，因此产生了一批连锁报错。

修复，容器内重编 protobuf 3.21.12 覆盖：

```bash
cd /tmp
curl -L -o pb.tar.gz https://github.com/protocolbuffers/protobuf/releases/download/v21.12/protobuf-cpp-3.21.12.tar.gz
tar xf pb.tar.gz && cd protobuf-3.21.12

./configure --prefix=/workspace/rank/thirdparty/protobuf \
  CXXFLAGS="-fPIC -O2 -D_GLIBCXX_USE_CXX11_ABI=0"
make -j$(nproc)

# 备份旧版本
mv /workspace/rank/thirdparty/protobuf/include /workspace/rank/thirdparty/protobuf/include.bak3.7
mv /workspace/rank/thirdparty/protobuf/lib64_release /workspace/rank/thirdparty/protobuf/lib64_release.bak3.7
mv /workspace/rank/thirdparty/protobuf/bin/protoc    /workspace/rank/thirdparty/protobuf/bin/protoc.bak3.7

make install
mv /workspace/rank/thirdparty/protobuf/lib /workspace/rank/thirdparty/protobuf/lib64_release
```

`-D_GLIBCXX_USE_CXX11_ABI=0` 是这次为匹配现有 `.a` 使用的设置，并不是通用的 protobuf 编译要求。是否需要它，应核对其他 vendored 库的 ABI（`BLADE_ROOT` 里全局设置的是 `=1`，但我们这套 vendored 库实际编译时是 `=0`，混用会出现 `std::string` 链接失败）。

### #2 依赖使用了 C++14 特性

```
'exchange' is not a member of 'std'
'make_unique' is not a member of 'std'
```

`std::exchange` 是 C++14、`std::make_unique` 也是 C++14。`BLADE_ROOT` 里默认是 `-std=c++11`：

```python
# 只展示语言标准选项，其余配置保留。
cxxflags = [
    '-std=c++14',
]
```

### #3 bthread_attr_t 传值/传指针

```
cannot convert 'const bthread_attr_t' to 'const bthread_attr_t*'
```

`node.cpp:69`：

```cpp
// 错的
bthread_start_background(&tid, BTHREAD_ATTR_SMALL, b_func, args);
// 对的
bthread_start_background(&tid, &BTHREAD_ATTR_SMALL, b_func, args);
```

brpc 里 `BTHREAD_ATTR_SMALL` 是 `static const bthread_attr_t` 值，但函数签名要的是指针。

## 运行期问题

### 问题 1：Server 起来了，curl 卡死

`netstat` 显示监听正常，但 `curl localhost:16998` 无响应、连接 `CLOSE_WAIT`。

排查：

```bash
ps -T -p $(pgrep rank_server)   # 只有 2 个线程
```

线程数量取决于配置，不能以“是否有几十个线程”作为通用标准。本次排查需要关注的是，启动线程后 `impl.cpp` 又调用了：

```cpp
m_server.Start(...);
daemon(1, 1);                    // ← 这里炸
```

`daemon()` 涉及 `fork()`。多线程进程 fork 后，子进程只保留调用线程，其他线程持有的运行状态和锁可能无法继续正常工作。问题发生在启动线程之后再派生子进程；不能简单概括成“任何时候 fork 都会使 brpc 失效”。参见 [Linux fork 文档](https://man7.org/linux/man-pages/man2/fork.2.html)。

修复：删掉 `daemon()`，换成阻塞等待信号：

```cpp
m_server.Start(...);
m_server.RunUntilAskedToQuit();
```

### 问题 2：protoc 找不到 .so

```
protoc: error while loading shared libraries: libprotoc.so.32: cannot open shared object file
```

`readelf -d` 看 RUNPATH：

```
RUNPATH /workspace/thirdparty/protobuf/lib
```

老编译机的绝对路径被烧进了二进制。**修复**：

```bash
patchelf --set-rpath '$ORIGIN/../lib64_release' \
  /workspace/rank/thirdparty/protobuf/bin/protoc
```

`$ORIGIN` 是 ELF 的特殊变量，指**二进制所在目录**，这样无论包搬到哪都能找到 `lib64_release/`。

### 问题 3：boost/core 子目录消失

新机重新 clone 后：

```
boost/core/ref.hpp: No such file or directory
```

先确认缺失文件是否真正提交过。`.gitignore` 不会让已跟踪的文件在 clone 时消失；它可能阻止未跟踪文件被加入版本控制。本次需要检查的规则是 `.gitignore` 里的 `core`，**这是 basename 匹配，会匹配到任意层级里叫 `core` 的目录或文件**，可能使新增的 `boost/include/boost/core/` 软链没有被提交。可用 `git ls-files` 和 `git check-ignore -v` 分别核对跟踪状态与匹配规则。

修复，`.gitignore` 里写**锚定路径**：

```
# 错的（basename 匹配）
core
core.*

# 对的（仅匹配仓库根的 /core 和 /core.*）
/core
/core.*
```

举一反三：`build` 也是常见的有歧义名字，最好都加 `/` 前缀锚定。

## 部署打包脚本

把二进制 + conf + 必要 .so + 启动脚本打成一个开箱即用的 zip：

```bash
#!/bin/bash
# tools/build_package.sh
set -euo pipefail

CONF_SRC="${1:?usage: $0 <conf_dir> [version]}"
VERSION="${2:-$(date +%Y%m%d_%H%M%S)}"

ROOT="$(cd "$(dirname "$0")/.." && pwd)"
BIN="$ROOT/build64_release/main/rank_server"
PKG="rank_server-$VERSION"
STAGE="$ROOT/dist/$PKG"

[[ -x "$BIN" ]]            || { echo "missing binary: $BIN"; exit 1; }
[[ -d "$ROOT/$CONF_SRC" ]] || { echo "missing conf:   $ROOT/$CONF_SRC"; exit 1; }

rm -rf "$STAGE"
mkdir -p "$STAGE"/{bin,conf,lib64_release,log}

cp "$BIN" "$STAGE/bin/"
cp -r "$ROOT/$CONF_SRC"/. "$STAGE/conf/"
install -m 0755 "$ROOT/tools/start.sh" "$ROOT/tools/stop.sh" "$STAGE/bin/"

# 打包 .so，剔除 glibc 系
ldd "$BIN" | awk '/=>/ && $3 ~ /^\// {print $3}' \
  | grep -Ev '/(ld-linux|libc|libm|libdl|libpthread|librt|libgcc_s|libstdc\+\+|libgomp)\.so' \
  | xargs -I{} cp -L {} "$STAGE/lib64_release/"

patchelf --set-rpath '$ORIGIN/../lib64_release' "$STAGE/bin/rank_server"

cd "$ROOT/dist" && rm -f "$PKG.zip" && zip -qr "$PKG.zip" "$PKG"
echo "OK: $ROOT/dist/$PKG.zip ($(du -sh "$PKG.zip" | cut -f1))"
```

几个关键决策：

1. **三方库 .a 都已静态链进 82M 的二进制**，运行期只剩 `libssl.so.3` / `libcrypto.so.3` / `libz.so.1` + glibc 系。前三个跨发行版可能版本不一致 → 打包；后者必须用目标机自己的 → 黑名单剔除。

2. **`-L` 解软链**：`libssl.so.3` 通常是软链到 `libssl.so.3.0.x`，不解软链的话 zip 里只有空软链，部署解压后链接断掉。

3. **RPATH 用 `$ORIGIN`**：能减少对安装绝对路径的依赖，但目标机的架构、glibc 与动态库 ABI 仍需兼容。

4. **conf 目录作为参数传入**：`bash build_package.sh conf/demo`，将来加 `conf/prod`、`conf/canary` 不用改脚本。

部署机：

```bash
unzip rank_server-v1.0.zip
cd rank_server-v1.0
./bin/start.sh
```

## 框架内部的 3 个值得注意的设计点

工程跑通之后回头看代码，DAG 调度部分有几处实现挺有意思，既看得出当年的取舍，也能识别出潜在风险。

### Node::skip() — 双重否定的认知负担

`Node` 是 DAG 节点的基类，框架在执行某个节点时，会先调用其 `skip()` 决定是否真正执行业务逻辑：

```cpp
void Node::run(std::shared_ptr<GraphContext> context) {
    if (!skip(context)) {
        do_service(context);
        if (type() == "cpu") run_output_nodes_if_ready(context);
    } else {
        run_output_nodes_if_ready(context);   // 跳过业务，但仍要触发后继节点
    }
}

bool Node::skip(std::shared_ptr<GraphContext> context) {
    return false;       // 默认不跳过 → do_service 总是执行
}
```

设计上是想让子类按需重写 `skip()` 返回 `true` 来短路某些条件下的执行（比如灰度开关、缓存命中等）。但调用点是 `if (!skip())`，**双重否定**：

> “如果不跳过就执行” ←→ 子类覆盖时要思考“我什么时候返回 true 让自己不执行”

这种 API 命名在维护期会反复让人卡壳。更直观的写法是把语义正向化，例如：

```cpp
virtual bool should_run(...) { return true; }   // 默认执行；子类按需返回 false
// run() 内: if (should_run(ctx)) do_service(ctx);
```

旧代码曾出现 `if (skip())` 却进入执行分支的写法，与函数名相反。测试应分别覆盖 `skip()` 为真和为假，并断言业务是否执行。正向命名可以减少阅读负担，但不能替代分支验证；也不能认定所有带 `skip` 或 `disable` 的接口都需要改名。

### CacheWrapper<T> — `volatile` 假装的“原子双缓冲”

热更新场景常用双缓冲：写线程把新数据写到备用 buffer，再原子切换索引；读线程拿到的要么是新数据要么是旧数据，绝不会读到半更新状态。代码里这套实现长这样：

```cpp
template <class T>
class CacheWrapper {
protected:
    volatile unsigned int m_index;
    T m_data[2];

public:
    T& getData() {
        return m_data[m_index % 2];                    // 读
    }

    void updateData(T& data) {
        int tmp = m_index + 1;
        m_data[tmp % 2] = data;                         // 1) 写备用槽
        ++m_index;                                       // 2) 切换索引
    }
};
```

这里需要分别检查索引同步和数据的存储期。`volatile` 不提供 C++ 线程间同步；读写同一非原子对象而没有适当同步，可能形成数据竞争，不能因为在 x86 上暂时没有崩溃就认定正确。

**只把索引改成 atomic 仍然不够。** 假设读线程拿到槽 0 后尚未读完，写线程连续更新两次，第二次又写回槽 0。即使索引使用 release/acquire，读写仍可能同时碰到同一个 `T`。多写线程之间也有竞争，单独给索引加 CAS 无法解决槽位的存储期问题。

没有证据表明锁成为瓶颈时，可以先用互斥锁保护整个访问，并返回独立副本：

```cpp
#include <mutex>

template <class T>
class CacheWrapper {
    mutable std::mutex mutex_;
    T data_{};

public:
    T getData() const {
        std::lock_guard<std::mutex> lock(mutex_);
        return data_;
    }

    void updateData(const T& data) {
        std::lock_guard<std::mutex> lock(mutex_);
        data_ = data;
    }
};
```

这个示例假定 `T` 的复制能得到调用方可独立读取的数据。如果 `T` 内部仍共享可变指针，还需处理指向对象的同步。数据较大时，也可研究发布不可变快照并持有其所有权的方案；无论采用哪种方式，都要回答“旧读者何时读完”，不能只回答“新索引何时可见”。

### DynamicConfLoadMgr — mtime 轮询 + 2 秒延迟

配置热更新的实现非常朴素：

```cpp
void DynamicConfLoadMgr::run() {
    while (m_state) {
        sleep(m_interval);                       // 默认 2 秒
        // ...遍历每个注册的 Conf 元素
        for (auto* e : m_elementVec) {
            e->refreshConfig();
        }
    }
}

bool ConfElement::refreshConfig() {
    struct stat st;
    stat(m_path.c_str(), &st);
    time_t now = time(nullptr);
    if (st.st_mtime > m_fileTime &&
        now > st.st_mtime + 2) {                 // 等 2 秒，确保写入完成
        m_fileTime = st.st_mtime;
        return parseConfig();
    }
    return false;
}
```

设计要点：

- **基于 `st_mtime` 的轮询**，不依赖 `inotify`/`fanotify` 这类内核事件，跨平台、易理解，但延迟取决于轮询周期（这里 2 秒）
- **“now > mtime + 2”** 是一个朴素的“写入完成”判定，配置文件被 `vim`/`scp` 落地时通常是分多次 `write()`，立即 stat 拿到的可能是不完整文件。等 2 秒能粗略避开这种情况，但不是绝对安全（大文件 / 慢盘可能写超过 2 秒）
- 注册的 `ConfElement` 子类（GraphConf / NodeConf / ServiceConf / LogLevelConf）各自实现 `parseConfig()` 调用对应 manager 的 `init()`，**重新加载时是整体替换**，没做增量 diff；如果某个 manager 内部不是双缓冲实现，热更新瞬间会有短暂“配置撕裂”窗口

更稳妥的实现方向：

1. 用 `inotify_add_watch(IN_CLOSE_WRITE | IN_MOVED_TO)`，事件驱动取代轮询，`IN_CLOSE_WRITE` 表示一个可写文件描述符关闭，并不保证没有其他写者或随后再次写入
2. 配合一个 staging file pattern：写入方先写 `xxx.tmp` 再 `rename()` 成 `xxx.xml`（同一文件系统内用原子替换发布完整文件；持久性要求另行处理）
3. parseConfig 出错时保留旧配置而不是替换成空，避免因为一次坏配置把服务搞挂

另外这段代码里还有个隐蔽的 bug：

```cpp
boost::unique_lock<boost::mutex>(m_mutex);    // ← 临时对象，下一行就析构了
```

这是一个**未命名的临时对象**，构造完立即析构，锁进了又立刻出来。等价于没加锁。正确写法是给 lock 起个名字：

```cpp
boost::unique_lock<boost::mutex> lock(m_mutex);
```

具名 RAII 对象会在作用域结束时析构，临时对象通常在当前完整表达式结束时就析构。检查锁的存活范围，比只看有没有写锁类型更重要。

## 再换一台机器时，按什么顺序检查

先核对依赖的架构、编译器 ABI 和生成器版本，再做全量构建；运行后检查工作线程、动态库路径和配置加载。不要把编译通过当成并发正确性的证据，缓存快照与热更新还需要独立的存储期和失败处理设计。

本文是特定工程快照的排查记录。文中的库版本和路径用于解释当时的错误；移植另一份工程时，应保留详细编译命令和产物清单，再决定是否沿用修复。
