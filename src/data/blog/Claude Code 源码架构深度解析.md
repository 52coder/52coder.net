这篇从官方 `code-review` 插件入手，读一遍自动代码审查的工作流程：它怎样取得变更、分配检查任务、复核疑似问题，以及把结果定位到具体代码。

标题里的“源码”需要限定范围：这里能读到的是公开插件的命令定义，不能据此还原 Claude Code 核心运行时。插件里的 Markdown 描述要做什么，真正的工具调用、会话管理和执行过程由宿主负责。

本文于 2026 年 11 月 8 日对照了 [官方插件仓库中的命令文件](https://github.com/anthropics/claude-plugins-official/blob/main/plugins/code-review/commands/code-review.md)。该链接指向会变化的 `main` 分支；复现某次行为时，还应记录插件提交和 Claude Code 版本。旧版文章里的固定文件大小和“工业级”判断已删去，它们不能说明审查质量。

## 先分清插件文件和运行时

可以把插件理解成一份“审查任务说明”。它规定输入、分工和结果格式，却不包含完整的执行引擎。

| 文件或组件                | 在这里负责什么                     |
| ------------------------- | ---------------------------------- |
| 插件元数据                | 让宿主识别插件的名称、描述和版本   |
| `commands/code-review.md` | 描述代码审查步骤和可用工具         |
| Claude Code 运行时        | 读取指令、调用模型与工具、管理会话 |
| GitHub CLI 与评论工具     | 取得变更信息、读取或发布审查结果   |

所以，读命令文件时应追问“这一步拿到了什么，交给下一步什么”。至于任务如何调度、如何重试、怎样压缩上下文，除非另有实现证据，不应从这份文件反推内部架构。

## 一次审查怎样推进

当前命令文件先检查审查是否需要继续，再收集适用的 `CLAUDE.md` 和变更摘要。随后安排多个任务从项目约定和代码错误两个角度检查，再对候选问题复核、筛选。

最终结果先输出到终端。是否发布 GitHub 评论还取决于 `--comment` 参数；有问题时可以创建行内评论，没有问题时则按命令约定处理摘要。流程与输出行为应以对应版本的[命令定义](https://github.com/anthropics/claude-plugins-official/blob/main/plugins/code-review/commands/code-review.md)为准。

这套安排里，有三个值得单独拆开的设计。

### 收集项目约定时，先判断适用范围

假设仓库结构如下：

```text
CLAUDE.md
server/
  CLAUDE.md
  order.cpp
web/
  checkout.ts
```

审查 `server/order.cpp` 时，要考虑根目录和 `server/` 下的规则。`server/CLAUDE.md` 里的 C++ 命名要求，不能直接拿来指责 `web/checkout.ts`。

一条有用的规范问题应该写清楚三件事：哪条规则适用、哪段新代码违反了它、为什么这不是已有的例外。只写“代码不符合最佳实践”，维护者很难判断该不该改。

### 多个检查任务可以分工，但结果仍要验证

并行任务的用途是让不同检查角度分别保留注意力。例如一个任务看目录规则，另一个看空值分支或错误处理。把同一段代码交给多个模型，并不自动得到相互独立的证据：它们可能受到相同上下文和相似推理习惯的影响。

以这段示意代码为例：

```cpp
if (items.empty()) {
    return items.front();
}
```

“空容器仍访问首元素”有明确的触发条件。复核者应检查这是否属于新改动、`items` 的实际类型是什么、该分支能否到达。换成更复杂的业务代码，还要继续找调用约束，而不能因为另一个任务说“确定”就结束核查。

插件为了减少误报，会限制某些检查的范围。这是一种取舍：它能减少脱离上下文的猜测，也可能漏掉跨文件、依赖特定状态才出现的错误。评价效果要看真实审查结果，不能只数用了几个任务。

### 把“发现问题”和“发布评论”分开

内部候选问题可以很多，发布到代码审查页面的内容应该经过整理。否则，同一个问题可能被重复评论，甚至把尚未核实的猜测留给作者处理。

一个可复核的评论至少需要：

- 触发条件，例如空列表、超时或重复请求；
- 具体后果，例如崩溃、重复扣费或丢失更新；
- 对应文件和行，以及支持判断的调用或规则。

链接最好固定到完整提交哈希。若只指向分支头，作者又推送了一次代码，原评论对应的行可能已经变了。

## 工具声明不能代替所有权限控制

命令的 `allowed-tools` 列出了若干 `gh` 操作和行内评论工具。因此，“所有 GitHub 操作都通过 gh 完成”并不准确，评论也可能经过 MCP 工具。

MCP 规定工具如何被发现和调用，不代表接入的工具天然安全。实际能访问哪个仓库、能否写评论，仍取决于工具实现、身份凭证和宿主权限设置。提示词里的“只做某件事”也不等于程序级访问控制。

读这部分时，可以用一个具体问题检验边界：即使模型误解了任务，它持有的工具权限是否允许执行不需要的写操作？这个问题要靠运行环境回答，单看 Markdown 无法得出结论。

## 为什么不把置信度当成正确率

旧版文章把“置信度评分”写成了这套系统的固定核心。对照当前命令后，更准确的描述是：它要求复核疑似问题并过滤未通过的结果，不能概括成某个永久不变的分数阈值。

即使其他版本给出 90 分，也不能直接解释为“有 90% 的概率正确”。要得到这样的概率含义，需要在有标注的样本上检验校准情况。对维护者而言，触发条件、最小复现和代码证据通常比一个孤立分数更有用。

## 怎样借用这套思路

如果想给自己的项目做一个审查命令，可以先只处理一种容易核实的问题，例如新引入的空值访问，或者一条明确的目录规则。为它准备几份小改动：有错误的、已经修好的，以及看似错误但受调用约束保护的。

记录每次报告了什么、漏掉了什么、需要花多久复核。等误报原因清楚了，再决定是否增加检查角度和并行任务。这样读完插件，得到的是一套可以试验的审查流程，而不是“任务越多就越可靠”的结论。

继续阅读时，可对照 [Claude Code 插件文档](https://code.claude.com/docs/en/plugins)区分命令、技能和工具各自的作用；本文的重点仍是 `code-review` 这份公开命令如何组织工作。
