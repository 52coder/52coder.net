一个服务要同时请求三个下游接口，每个接口都要等一会儿。最直接的写法是请求 A，等 A 返回，再请求 B、C。代码好读，但等待时间叠加了。

协程让我们保留这种顺着读的写法，同时在等待期间把执行机会交给其他任务。要理解它，先分清“程序正在计算”和“程序正在等结果”。

## 等待期间，线程在做什么

普通阻塞调用会让当前线程停在调用处。比如读取网络数据时，对方还没发来数据，线程暂时就无法继续处理别的请求。

![阻塞调用示意](@/assets/images/blocking.png)

一种办法是为不同请求安排不同线程。线程 A 等待时，线程 B 继续工作。线程池正是常用方案，但线程数量和内存、调度开销都需要控制。

线程的栈大小取决于操作系统、运行时和创建参数。Linux 的默认值还与进程启动时的资源限制有关，不能一概写成“每个线程固定占 8 MB 栈、64 MB 堆”。预留的虚拟地址空间，也不等于实际驻留的物理内存。具体约定见 [pthread_create 文档](https://man7.org/linux/man-pages/man3/pthread_create.3.html)。

## 一个线程也可以照看多个请求

换一种安排：发出 A 的请求，发现结果没准备好，先记下 A 的进度；接着处理 B、C。等 A 的数据到了，再从刚才停下的地方继续。

![非阻塞方式下的任务交替](@/assets/images/non-blocking.png)

这里有两项工作。I/O 机制负责通知“哪个请求可以继续”，程序负责保存“继续后做什么”。事件循环和回调可以完成这件事，但业务步骤一多，逻辑容易散在不同回调里。

协程把暂停和恢复表达在函数内部。它挂起时，运行时保留恢复所需的状态；条件满足后，再恢复执行。

![协程在等待处让出执行机会](@/assets/images/coroutines.png)

## 用两个等待任务看清执行顺序

下面用 Python 的 `asyncio` 演示。`sleep` 只是模拟等待，没有访问网络。保存为 `coroutine_demo.py` 后运行 `python3 coroutine_demo.py`。

```python
import asyncio
import time

async def fetch(name):
    print(f"开始 {name}")
    await asyncio.sleep(1)
    print(f"完成 {name}")
    return name

async def main():
    started = time.perf_counter()
    results = await asyncio.gather(fetch("A"), fetch("B"))
    print(results)
    print(f"耗时约 {time.perf_counter() - started:.1f} 秒")

asyncio.run(main())
```

通常会先看到“开始 A”“开始 B”，约一秒后再看到两个完成消息。A 在 `await asyncio.sleep(1)` 处挂起，B 才有机会开始等待。两个等待重叠了，所以总时间接近一秒，加上调度开销。

如果改成 `await fetch("A")` 后再写 `await fetch("B")`，它们仍会依次执行，总时间接近两秒。**写了 async，并不自动意味着任务会并发运行。** 这里是 `gather` 安排了两个任务的并发等待。相关接口见 [asyncio 协程与任务文档](https://docs.python.org/3/library/asyncio-task.html)。

## 并发不等于同时计算

上面的两个任务可以在同一线程中交替推进，但同一时刻仍只有一个在执行 Python 代码。协程减少的是“等着没事做”的时间，不会让一段 CPU 计算凭空加速。

如果把 `await asyncio.sleep(1)` 换成 `time.sleep(1)`，当前线程会被阻塞，其他任务也得跟着等。遇到只有阻塞接口的库，可以考虑用线程池承接；Python 的 `asyncio.to_thread` 就提供了这样的入口。计算密集型工作则要另外考虑进程、能释放解释器锁的原生库，或其他并行机制。

## 协程怎样保存进度

“保存栈指针，再切换栈”只描述了部分协程实现。常见的实现有两类：

| 类型     | 暂停时主要保留什么                     | 理解时要注意什么                     |
| -------- | -------------------------------------- | ------------------------------------ |
| 有栈协程 | 独立的调用栈及相关执行上下文           | 具体栈大小、切换方式由库或运行时决定 |
| 无栈协程 | 恢复位置、跨暂停点存活的局部变量等状态 | 不需要为每个协程保留一套独立调用栈   |

C++20 的语言级协程属于无栈协程。编译器把恢复所需的状态放进协程帧，`co_await` 等语法描述暂停点；怎样等待网络、交给哪个线程恢复，还需要库或运行时配合。语义可查 [C++ 协程定义](https://eel.is/c++draft/dcl.fct.def.coroutine)。

I/O 接口也不能混成一类：Linux 的 epoll 主要报告就绪事件，Windows 的 IOCP 报告完成事件。普通文件读写、网络读写对非阻塞和异步机制的支持不同，需要看具体 API。

## 用在服务里，还要补上哪些约束

假设同时发出一万个下游请求，协程创建成功并不代表下游能承受。仍然要限制并发数，为每个请求设超时，并决定取消后怎样释放连接和清理状态。

共享数据也仍需保护。即使只有一个事件循环线程，两个任务也可能在 `await` 前后交替修改同一份业务状态；如果任务跨线程恢复，还会涉及线程间的数据竞争。

选择协程时，可以先看业务是不是花了大量时间等待 I/O，以及所用库是否支持可挂起的调用。如果瓶颈在计算、数据库慢查询或下游容量，应该先处理那个瓶颈。协程最直接的收益，是让许多等待任务交替推进，同时把每个任务的步骤留在一段容易读懂的代码里。
